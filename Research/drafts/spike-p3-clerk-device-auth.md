## Q1 — How current Fabric node pairing works end-to-end

**Identity a node presents:** an Ed25519 keypair generated client-side. The public key sent to the cloud is the raw 32-byte key, base64url-no-pad (server enforces length at `cmd/allternit-cloud-api/src/routes/runtime_pairing.rs:1195-1205`; client strips the 12-byte SPKI prefix at `cmd/gizzi-code/src/runtime/services/pairing/pairing.ts:209-214`). Proof of possession at exchange time is an Ed25519 signature over the exact string `allternit-runtime-pairing:{pairingId}:{challenge}` (`runtime_pairing.rs:1207-1209`, verified at `1128-1146`; client at `pairing.ts:205-229`).

**The flow (three legs, OAuth-device-shaped but Allternit-owned):**

1. **Create** — `POST /api/v1/runtime-pairings` (route `runtime_pairing.rs:189`, handler `220-235`), unauthenticated. Body: `{ name, runtimeType, hostname?, platform?, version?, publicKey, capabilities[] }`. Response 201: `{ pairingId, deviceCode, userCode, challenge, verificationUrl, expiresAt, pollIntervalSeconds }` (TTL 10 min, `PAIRING_TTL_MINUTES`, `runtime_pairing.rs:29`). `verificationUrl = {ALLTERNIT_PLATFORM_URL}/pair?code={userCode}`, default platform `https://platform.allternit.com` (`331-337`). `userCode` is `XXXX-XXXX` from Crockford-safe alphabet (`1363-1372`).
2. **Approve** — a human in a browser with a **Clerk session JWT**, or an already-paired desktop whose **device token** acts as approver (`approver_from_headers`, `runtime_pairing.rs:1050-1082`). Endpoints: `GET …/code/:code`, `POST …/code/:code/approve`, `POST …/code/:code/deny` (routes `191-199`). Self-approval lanes for `hosted` / `vps`+`byo_bootstrap_token` / `provisioned` bypass the browser via one-time bootstrap tokens (`242-266`, validators `1223-1347`).
3. **Exchange (poll)** — `POST /api/v1/runtime-pairings/exchange` `{ pairingId, deviceCode, signature }`, unauthenticated; the row is keyed by `pairing_id` + `sha256(deviceCode)`. Statuses: **410** `expired_token`, **428** `authorization_pending`, **403** `access_denied` (`runtime_pairing.rs:517-537`), **429** with `retry_after` (client handling `pairing.ts:267-272`), **200** → `{ runtimeId: "rt_<uuid>", userId, userEmail, organizationId?, deviceToken: "allternit_runtime_<48B b64url>", tokenType: "Bearer", expiresAt, capabilities[] }` (prefix constant `runtime_pairing.rs:38`, TTL **90 days**, `CREDENTIAL_TTL_DAYS` line 30).

**Nodes vs users authentication split** (the Clerk question): the cloud API has two disjoint credential systems. Users present a Clerk session JWT (`clerk::user_from_headers`, fallback API-key user resolution, `runtime_pairing.rs:1067-1079`). Nodes present the device token, recognized by the `allternit_runtime_` prefix — "other routes use it to tell a device token apart from a Clerk session JWT" (`runtime_pairing.rs:36-38`) — resolved via `runtime_device_for_token` and `authenticate_runtime_token` (also the relay auth, `runtime_relay.rs:74,634`). **The node never sees or holds any Clerk token**; this separation is stated verbatim in the operator doc `cmd/allternit-cloud-api/RUNTIME_PAIRING.md`: "binds Allternit desktop and VPS runtimes to a human account without giving the runtime the human's Clerk session token."

**Keypair/token storage (three separate silos today):** gizzi-code `<data>/runtime-device.json` (`pairing.ts:105-107`, atomic 0600 write `119-129`); agent-daemon `~/.config/allternit/runtime-identity.json` (`cmd/agent-daemon/src/index.ts:10-11,62-66`); Desktop `app.getPath('userData')/auth/runtime-identity.json` (`surfaces/allternit-desktop/src/main/auth-manager.ts:197`). Keypair is reused across re-pairs; only the token rotates (`pairing.ts:24-26`).

**The runtimeType enum** — this is where `"ao"` would go: validated as a plain string match at `runtime_pairing.rs:1154-1161`:

```rust
if !matches!(request.runtime_type.as_str(),
    "desktop" | "vps" | "hosted" | "provisioned" | "ios") { … }
```

Adding `"ao"` touches: this match, `runtime_device_kind` (`481-489` — `desktop`→`LOCAL`, `vps`→`PAIRED`; tested at `1389-1396`), and the runtime-devices list rendering. So contrary to the plan's "zero server changes" framing, `runtimeType "ao"` **is** a server-side change — small and additive, but deployed-code-dependent.

## Q2 — WSS relay protocol on the wire today

**Connection & auth handshake:** node opens `wss://api.allternit.com/api/v1/runtime-relay/connect/{runtimeId}` (route `runtime_relay.rs:293`; clients `agent-daemon/src/index.ts:241-243`, `auth-manager.ts:1184-1186`). First frame must be `{"type":"authenticate","runtime_id":"rt_…","device_token":"allternit_runtime_…"}` (enforced in `runtime_socket`, `runtime_relay.rs:618-634`); server validates token+id match and replies `{"type":"authenticated","runtime_id":"…"}` (`679-691`). Server pings every 25 s, node answers `{"type":"pong"}` (client `index.ts:267-268`). On drop, tunneled sockets close with 1012; client backoff 1 s→30 s (`index.ts:271-278`). Single-instance guard: `if (!identity || relay) return` (`index.ts:240`) — a second relay from the same runtime id routes to the *latest* hub registration.

**HTTP tunnel:** cloud→node `{"type":"request","request_id","method","path","headers":{…},"body","body_encoding":"utf8"|"base64"}` (`CloudMessage` enum, `runtime_relay.rs:82-120`). The node forwards to its loopback gateway `http://127.0.0.1:8013{path}` (`LOCAL_GATEWAY_URL`, `index.ts:14,314`), injecting `Authorization: Bearer <deviceToken>` **only if the envelope didn't carry the caller's Clerk JWT** (so the local gateway can authenticate as the end user — `index.ts:298-308`), plus `X-Allternit-Desktop-Access-Token`, `X-Allternit-User-Id`, `X-Allternit-User-Email`, `X-Allternit-Tenant-Id`. Response streams back as `response_start {request_id,status,headers}` → N× `response_chunk {request_id,body(base64),body_encoding:"base64"}` → `response_end` (`index.ts:320-341`); legacy single-frame `response` still accepted server-side. Server-side timeout 90 s (`RELAY_TIMEOUT`, `runtime_relay.rs:77`), body cap 5 MB (line 78), 340 s carve-out for video-generate.

**Browser → cloud → node:** `POST /api/v1/runtime-devices/:id/proxy` (Clerk or API-key authed, owner-scoped; `BrowserProxyRequest` `runtime_relay.rs:167-178`, handler `798-822`, relay core `relay_request_to_runtime` `841-952`). Enforcement before relaying: path allow-list `/api /viz /sandbox /vm-session /rails /stream /terminal /mcp /platform /metrics /alabs /cowork /webhooks /ws /panes /status /health /v1` (`is_allowed_runtime_path`, `1039-1069`); per-path capability check (`required_capability`, `1071-1105` — health/status/metrics→`runtime:connect`, provider→`providers:*`, terminal/pty/panes→`runtime:terminal`, files/workspace→`runtime:files`, remote-control→`runtime:remote_control`, else `runtime:execute`); request header allow-list incl. `authorization` — "forwarding their Authorization lets the box's gizzi-code validate the end user's JWT" (`filtered_headers`, `1107-1127`); response header allow-list mirrored in the node client (`index.ts:316-319`). Wake-on-demand (hosted only) starts the container and polls up to 30 s, else 503 `runtime_warming`/`runtime_offline` / 504.

**WebSocket tunnel:** cloud→node `socket_open {socket_id,path,headers}` / `socket_data` / `socket_close`; node dials `ws://127.0.0.1:8013{path}` and answers `socket_ready`, then relays frames both ways (protocol doc-comment `runtime_relay.rs:16-47`; node `index.ts:359-423`). Browser can't set `Authorization`, so it mints a single-use ticket: `POST …/socket-ticket {path}` → `{ticket, expiresInSeconds:30}`, then `GET …/socket?ticket=…` upgrades (`issue_socket_ticket` `319-386`, `connect_browser_socket` `472-485`); browser gets a sentinel text frame `{"type":"allternit_socket_ready"}`.

**PWA side:** QR content is `https://fabrictransport.allternit.com/?runtime=rt_…` (`surfaces/ai.allternit.com/src/lib/fabric-session-pwa.ts:8,12-16`, rendered `FabricSessionQrCard.tsx:18,35`, 168 px, level M). `?runtime=` persists to `localStorage["allternit.active-runtime-id"]` after regex validation (`src/lib/runtime-target.ts:26-43`). Machine list = `GET /api/v1/runtime-devices` (Clerk bearer), 10 s poll, offline grace 10 min (`src/components/dispatch/useRuntimes.ts:86,150,178-180`). The SDK turns every call into `POST {cloud}/api/v1/runtime-devices/{runtimeId}/proxy` when a runtimeId is set (`sdk/allternit-sdk/src/ai-runtime/runtime/index.ts:167-202`), and does SSE as one proxied HTTP GET with `Accept: text/event-stream` — explicitly not EventSource, not the socket-ticket path (`393-428`).

## Q3 — What exists to reuse for ao; the headless auth flow

**There is no Rust node client anywhere in the repo.** Grep for `runtime-relay/connect` hits only: the server route, docs (`cmd/allternit-cloud-api/RUNTIME_PAIRING.md`, `surfaces/docs/`), and the two TypeScript clients. What exists to port:

| Piece | Location | Size/notes |
|---|---|---|
| Reference full node (pairing + heartbeat + rotation + relay + socket tunnel) | `cmd/agent-daemon/src/index.ts` | 446 lines, self-contained, production-deployed on VPS boxes |
| Pairing-only client (cleanest, best-commented wire contract) | `cmd/gizzi-code/src/runtime/services/pairing/pairing.ts` | 358 lines; wire shapes pinned in header comment (`10-22`) |
| Electron-flavored second relay copy | `surfaces/allternit-desktop/src/main/auth-manager.ts` (`1181-1225` relay, `1087-1107` rotate, `1110-1133` heartbeat) | longest, most edge-case handling; worst to port |
| Push-notify trigger (event → `/notify`) | `cmd/gizzi-code/src/runtime/integrations/remote-control-push.ts` | 25-133; auth choice secret-vs-device-token at 45-58 |

The ao-engine fork has nothing Fabric-side yet (`grep -ri fabric src/` in `infrastructure/executor/ao-engine` = no hits); its P1 work is the `ao` CLI contract (`src/cli/ao.rs`).

**The headless-CLI auth flow — premise correction:** this is **not Clerk's OAuth device flow**. Clerk appears exactly once: authenticating the approving human's browser session at the approve endpoint. The device-code flow (create / approve / exchange) is Allternit's own protocol implemented in `runtime_pairing.rs`; there are no Clerk device-flow endpoints, no Clerk token storage, no Clerk refresh. For a headless binary:

- **Endpoints to implement:** `POST /api/v1/runtime-pairings` → `POST /api/v1/runtime-pairings/exchange` (poll, honor 429 `retry_after`, die on 410/403) → then the lifecycle loop `POST …/heartbeat` (30 s cadence; **401/403 ⇒ revoked**, `agent-daemon/src/index.ts:215-225`), `POST …/rotate` (proactive, within 7 days of expiry; `ROTATION_SKEW_MS` `index.ts:13,227-237`; gizzi uses a 30-day window `pairing.ts:46,164-203`), `POST …/revoke-self` on unpair.
- **Token storage:** no refresh token exists; "refresh" = rotation, which replaces the 90-day token outright. The server keeps the rotated-out hash valid for **15 min** (`ROTATION_GRACE_MINUTES`, `runtime_pairing.rs:31-35`) so two components sharing one identity self-heal — this exists precisely because gizzi-code and agent-daemon on BYO boxes share a device row. Store as JSON 0600 with atomic rename (pattern at `pairing.ts:119-129`).
- **Browser opening** is best-effort (`open` package, `pairing.ts:317-325`, guarded by `GIZZI_PAIR_NO_BROWSER`) — ao must detect headless (no `SSH_TTY`-adjacent display / a `--no-browser` flag) and just print URL + code.

## Q4 — Design fork: in-process translation vs loopback shim

**Grounded facts:**

1. The engine's API is ND-JSON request/response over a unix socket — `interprocess::local_socket`, socket file mode 0600, 1 MB initial-request cap (`infrastructure/executor/ao-engine/src/api/server.rs:27-32`). Clients connect per request (`src/api/client.rs:96-97` → `ipc::connect_local_stream(socket_path())`, path from `src/api/mod.rs:98-100`). Subscriptions (`src/api/subscriptions.rs`) ride the same socket. **No HTTP, no WebSocket, no tokio in the engine socket server** (std thread + polling).
2. The relay contract is written against an HTTP+WS loopback gateway: the node dials `http://127.0.0.1:8013`/`ws://…` (`agent-daemon/src/index.ts:14,314,370`), and the cloud side doesn't care what's behind it — but the proven node behavior (path guard, identity-header injection, chunked base64 streaming, socket-tunnel semantics, 1012 teardown) is all expressed as HTTP proxying.
3. The existing loopback gateway on 8013 is `cmd/allternit-api` — a **Rust axum binary** (workspace deps already include axum with `ws`, tokio, tokio-tungstenite; `cmd/allternit-api/Cargo.toml`), default port 8013 (`src/config.rs:249`), bound to **`0.0.0.0`** (`src/main.rs:931` — worth flagging: a local gateway listening on all interfaces). It serves rails/sessions/terminal/vm-session/stream-ws and has **zero references to herdr/ao-engine** — there is no existing HTTP→engine-UDS bridge to reuse.
4. ao needs an HTTP surface anyway: the Fabric PWA session pickup targets `/api/v1/*` on the node, P5's visibility panel and P6's UHP Responses API are HTTP/SSE-shaped. The loopback shim is not P3-only scaffolding.

**Recommendation: loopback shim.** ao runs an axum HTTP+WS gateway on `127.0.0.1` (its own port, distinct from 8013 to coexist with a running Desktop sidecar; port configurable), translating to the engine socket API in-process (the binary embeds the engine, so the shim can call the engine's API channel directly — no UDS hop). The relay client is then a **line-faithful Rust port of `agent-daemon/src/index.ts`**. Reasoning:

- *Fidelity:* porting the relay handlers is mechanical and their behavior is triple-proven against the deployed cloud (agent-daemon, desktop, and server-side serde tests at `runtime_relay.rs` — the socket-tunnel envelopes are already pinned in server tests, cited in the prep memo at 1204-1278). In-process translation would re-derive every one of those semantics (chunking boundaries, header injection rules, 1012 teardown, backoff) against `pane.*`/`agent.*` RPC with no behavioral oracle, and each re-derived rule is a drift risk on a security-relevant path.
- *The request envelope is HTTP-shaped.* Mapping `{method, path, headers}` onto engine RPC is a hand-written, lossy translation per route family; mapping it onto `reqwest` to `127.0.0.1` is zero-translation.
- *Reuse across phases:* the same shim serves PWA session pickup (P3), the visibility panel (P5), and UHP (P6). In-process translation would be duplicated or thrown away.
- *Honest counterweight:* a shim costs an axum runtime inside ao, a TCP port, and loopback auth handling (bearer tokens on 127.0.0.1 — mitigated by binding loopback-only, unlike allternit-api's 0.0.0.0). It also double-serializes (JSON → HTTP → JSON → engine). These are real but small; the fidelity and reuse arguments dominate. **Decision recorded below (D4).**

## Q5 — Open questions / blockers for the P3 spec

1. **`runtimeType "ao"` is a server change.** Confirmed at `runtime_pairing.rs:1154-1161` + `runtime_device_kind` (`481-489`). Plan §5 says both "server side unchanged" and "runtimeType 'ao' must be added to the API enum" — contradictory; the spec must either schedule the additive enum change or ship pairing as `desktop` (kind `LOCAL`). Cannot be resolved from this repo alone; needs a deploy of `allternit-cloud-api`.
2. **Deployed-vs-repo skew (unverified).** No live calls were made to `api.allternit.com` in this spike. All shapes are triple-corroborated in source (Rust server + two TS clients + server serde tests), but a pre-spec smoke (`curl` the pairing create/info endpoints, expect clean 4xx) is still owed.
3. **Identity multiplicity decision.** ao's own row (clean lifecycle, fragments the PWA machine list, consumes an active-device slot — cap check cited in prep memo at `runtime_pairing.rs:559-563`) vs sharing an existing identity file (couples rotation; the 15-min grace covers races, not outages). No code blocker; a spec decision (D1 below).
4. **Headless approval is browser-only.** The bootstrap-token self-approval lanes (`hosted`/`provisioned`/`byo_bootstrap_token`, `runtime_pairing.rs:242-266,1223-1347`) are minted by provisioning machinery, not available to a hand-installed ao. `ao fabric pair` on a fresh VPS must print URL+code and poll; no `open` when headless.
5. **Port coexistence.** Desktop's allternit-api takes 8013 (and binds 0.0.0.0). ao's shim needs a distinct default port and the relay client must not assume 8013. Env override pattern exists: `ALLTERNIT_GATEWAY_URL` (`agent-daemon/src/index.ts:14`).
6. **No wakeup path for sleeping machines.** Wake-on-demand exists only for hosted runtimes (`runtime_relay.rs:7-14`); ao nodes are `LOCAL`/`PAIRED` kind. A closed laptop is simply offline; the push worker notifies a human but cannot wake the node. This bounds the P3 "pickup from a second device" verify scenario to times when the ao host is awake.
7. **Push-trigger event source.** ao's blocked/approval detection (P5 dependency) must map to the four payload types `permission|question|completed|error`; the gizzi trigger (`remote-control-push.ts:89-133`) is the model. The worker's device-token auth path is confirmed (`services/remote-control-push/src/index.ts:388-429`, introspection at 139).
8. **Engine socket concurrency assumptions.** The engine socket server is single-request-per-connection with 5 s app-response timeout (`api/server.rs:29-32`); how the shim should multiplex concurrent PWA calls over that (pool connections? in-process channel instead of UDS?) needs a P1-informed decision — the P1 `ao` CLI exercises only sequential use.
9. **Relay rotation reconnect.** Rotation must force relay reconnect so the new token is used (`agent-daemon/src/index.ts:236` closes the socket post-rotate); the single-relay guard (`index.ts:240`) must be mirrored to avoid split-brain message routing.

## Binding design decisions for the P3 spec

1. **D1 — Own identity.** ao pairs under its own Ed25519 keypair and its own runtime-device row; it never reads gizzi-code's, agent-daemon's, or Desktop's identity files. State at `~/.agent-orchestrator/fabric/identity.json`, mode 0600, atomic temp-write+rename; keypair reused across re-pairs, token rotated in place.
2. **D2 — runtimeType.** ao requests `"ao"`; the spec includes the additive server change (enum match at `runtime_pairing.rs:1154-1161` + `runtime_device_kind`). Until that deploy lands, ao pairs as `"desktop"` (kind `LOCAL`) — the runtimeType is a single client-side constant, so there is no behavioral fork to maintain.
3. **D3 — Capabilities.** Request exactly the seven defaults (`runtime_pairing.rs:39-47`), including mandatory `runtime:connect`. No new capability is needed: `/api` prefix + `runtime:execute` covers any `/api/v1/…` the ao shim exposes; terminal/pty pickup needs `runtime:terminal` (already in the list).
4. **D4 — Seam = loopback HTTP+WS shim in-process over the engine API** (axum, `127.0.0.1` only, default port distinct from 8013, `ALLTERNIT_AO_GATEWAY_URL` override), **plus a line-faithful Rust port of `agent-daemon`'s relay client** forwarding to it. In-process translation of relay frames to engine RPC is rejected (fidelity, oracle, per-route lossy mapping, P5/P6 reuse).
5. **D5 — Wire fixtures as tests.** All relay/pairing envelopes become serde structs with golden-JSON round-trip tests in the ao crate, mirroring the server-side fixtures (`runtime_relay.rs` tests; `pairing.ts:10-22` contract comment) so protocol drift fails loudly on either side.
6. **D6 — Lifecycle loop.** Heartbeat 30 s; rotate within 7 days of expiry (agent-daemon skew, `index.ts:13`); 401/403 on heartbeat ⇒ treat as revoked, `revoke-self` best-effort, prompt re-pair; relay backoff 1 s→30 s; single relay instance per process; tunneled sockets close 1012 on relay drop; rotation forces relay reconnect.
7. **D7 — Headless pairing UX.** `ao fabric pair` prints `verificationUrl` + `userCode` and tries to open a browser only when a display is present and `--no-browser` wasn't passed; exchange polling honors `pollIntervalSeconds` and 429 `retry_after`; expires ⇒ clean error, re-pair. QR output after pairing = `https://fabrictransport.allternit.com/?runtime={id}` (shape from `fabric-session-pwa.ts:12-16`).
8. **D8 — Push notify via device token only.** ao POSTs `/notify` to `push.fabrictransport.allternit.com` with its device token (worker introspects via `/verify-token`, enforces runtimeId match, `remote-control-push/src/index.ts:388-429`) on blocked/approval/question events; ao never holds `NOTIFY_SECRET`.
9. **D9 — No server-side relay/proxy/PWA changes.** P3 is node-side only (plus the D2 enum add). The push worker, `runtime_relay.rs`, `runtime_pairing.rs` routes, PWA, and SDK are untouched.
10. **D10 — Verify scenario as specified in plan §5:** with the ao host awake and `ao fabric serve` running, pick up a live ao session from the PWA (`fabrictransport.allternit.com/?runtime=rt_…`) on a second device while the ao TUI is detached — no Desktop sidecar involved.

## What could NOT be determined from this code

- **Live deployed behavior.** Everything above is source-derived from main; `api.allternit.com` was not called. The deployed cloud-api may lag this repo — a 5-minute pre-spec smoke is owed (Q5.2).
- **Clerk-side details of the approval page** (`platform.allternit.com/pair`) — it lives outside this repo (platform surface); only its API contract (`approve`/`deny`/info endpoints) is visible here.
- **The ao↔shim multiplexing design** over the engine's single-request socket (Q5.8) — needs the P1 authors' knowledge of headless-server request routing; not derivable from the socket server code alone.
- **Whether an active-device quota would bite** with ao + Desktop + gizzi each holding a row on one machine — the cap value lives in `check_active_device_cap` (`runtime_pairing.rs:559-563` per prep memo) plus config; not exercised here.
- **No paired identity exists on this dev machine** at the canonical paths (no `~/.config/allternit/runtime-identity.json`; no Desktop `auth/runtime-identity.json`; no gizzi `runtime-device.json` found) — so end-to-end verification against the live cloud will start from a fresh `ao fabric pair`, which is actually the desired test.
